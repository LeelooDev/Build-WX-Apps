# 预览与发布

## 两种操作，性质完全不同

| | `wx_preview` | `wx_upload` |
|---|---|---|
| 做什么 | 生成预览二维码，扫码在真机看当前代码 | 上传为**体验版** |
| 影响范围 | 只有扫码的人 | 团队所有成员可见，占用该 appid 的开发版本槽位 |
| 是否需要确认 | 不需要 | **必须用户明确要求，且确认版本号和描述后才执行** |

## 预览（真机验证）

`wx_preview`。会先确保产物是最新的，再生成二维码图片。

用途：模拟器和真机表现不一致时（真机才有的性能问题、真机才生效的权限/支付/分享），让用户扫码在真机上验证。

二维码有时效，过期让用户说一声重新生成即可。

## 上传体验版

**这是对外可见的操作，默认不要主动做。** 只有用户明确说"上传""发体验版"时才执行，并且先确认清楚：

1. **版本号**——用户想用哪个。不要自己编，也不要沿用上一次的。
2. **版本描述**——这次改了什么。写清楚，团队成员靠它区分版本。
3. **代码状态**——当前工作区是不是就是要发的内容，有没有没提交/没验证的改动。

执行前建议先把该验的验了：`wx_run` 跑一遍、`wx_screenshot` 看关键页面、`wx_errors` 确认没有报错。上传一个带明显 bug 的体验版，团队每个人都会看到。

上传失败的常见原因：

- **未登录** → 让用户在开发者工具扫码登录
- **appid 没权限** → 当前登录的账号不是该小程序的开发者
- **包体积超限** → 主包超 2MB，需要分包或清理静态资源

## 正式发布

上传体验版之后，**提交审核和发布只能在微信公众平台网页端操作**，命令行做不到，也不该由 AI 代劳。告诉用户去 mp.weixin.qq.com 的「版本管理」提交审核即可。

## 无 GUI 的 CI 场景

如果用户要在 CI（GitHub Actions 等）里自动上传，开发者工具那套走不通——CI 上没有 GUI。这时应该用官方的 `miniprogram-ci` npm 包，它不依赖开发者工具，但需要在公众平台后台下载**上传密钥**并配置 IP 白名单。这属于 CI 配置范畴，按用户的 CI 平台给出对应方案。
